# AI Dev Workflow V1 — 开发全流程工作手册

> 不是让 AI 替你开发，而是让 AI 放大你的开发能力。

---

## 全流程总览

```
需求输入
  ↓
Phase 1 · 开发设计卡 ─── 想清楚再动手
  ↓
Phase 2 · Cursor 协作 ─── 拆任务 → 给上下文 → 局部生成
  ↓
Phase 3 · 验证闭环 ──── 自测 → 回归 → 可解释
  ↓
Phase 4 · 交付归档 ──── PRD + 审计 + Git
```

---

# Phase 1 · 开发设计卡

**准入规则：没有设计卡，不允许进入编码。**

### 模板

```
【功能名称】
一句话描述

【目标】
解决什么问题？

【输入】
- 数据源（表 / API / 文件）：
- 关键字段：
- 外部参数：

【输出】
- 返回什么数据 / 页面展示什么：
- 数据格式：

【核心逻辑】
1.
2.
3.
（3-5 行，说清楚主流程）

【边界条件】
- 空数据：
- 异常 / 超时：
- 并发 / 幂等：

【验证方式】
- 用什么输入验证输出正确
- 预期结果是什么
```

### 填写示例 — 埋点需求匹配门控

| 项 | 内容 |
|----|------|
| 功能 | 用户查询产品功能时，从埋点索引匹配候选事件，避免 LLM 幻觉 |
| 输入 | 用户 query 文本 + `event_tracking_index.json`（描述 / entity 取值 / 截图） |
| 输出 | 候选列表（desc, entity_name[], entity_type[], screenshot_url）或直通 SQL 生成 |
| 核心逻辑 | 1. 中文分词 + n-gram → 2. 逐条 score → 3. 取 top_k(score≥30) → 4. 有候选返回确认；无候选放行 |
| 边界 | 无候选 → 直通；已确认 → 注入上下文不重复匹配；min_score 过低 → 噪声 |
| 验证 | 输入"灵感续写"→ 返回候选；输入"DAU"→ 直通 |

# Phase 2 · Cursor 协作规范

**原则：人负责设计，AI 负责执行。**

### 四条红线

| # | 规则 |
|---|------|
| 1 | **先拆再问** — 把需求拆成独立子任务，逐个让 Cursor 生成，禁止一次「帮我写一个功能」 |
| 2 | **完整上下文** — 必须给出表结构、字段说明、已有代码、业务约束，不给上下文 = 不用 Cursor |
| 3 | **局部实现** — 让 Cursor 做函数级 / 模块级实现，不做全权负责 |
| 4 | **可解释** — 生成的代码自己必须能逐行解释，**不能解释 → 不允许提交** |

### Prompt 模板

#### 模板 A — 功能开发

```
你是一个资深后端工程师。

【背景】
我正在开发 {功能名称}。

【输入】
表结构：
{表名 + 字段名 + 类型 + 注释}

已有代码：
{相关函数/类的签名和关键逻辑}

【需求】
实现以下逻辑：
{设计卡中的核心逻辑 1/2/3}

【要求】
1. 只实现明确给出的逻辑，不要扩展
2. 不要假设不存在的字段
3. 输出完整代码 + 关键决策说明
4. 给出测试用例

【输出格式】
代码 + 逐段解释
```

#### 模板 B — Bug 排查

```
你是一个数据分析专家。

【问题现象】
{具体描述，如：查询"app端DAU"返回空结果}

【相关表】
{表名 + 字段列表}

【已知条件】
{已排查的信息：时间范围、参数值、已执行的 SQL 及结果}

请帮我：
1. 生成按关键维度拆分的排查 SQL
2. 定位可能异常来源
3. 给出修复思路

要求：
- SQL 必须可直接执行
- 不要省略字段和 WHERE 条件
```

#### 模板 C — SQL 优化

```
你是一个数据仓库专家（StarRocks 方言）。

【当前 SQL】
{SQL}

【问题】
{性能差 / 结果错 / 可读性差}

要求：
1. 不改变业务逻辑
2. 标注每处优化点
3. 输出优化后 SQL
```

# Phase 3 · 验证闭环

### 功能开发流程（5 步）

```
Step 1  填写设计卡 ──────── 没有卡 → 不允许开发
Step 2  用 Prompt 模板开发 ── 不允许裸问 Cursor
Step 3  自己理解代码 ─────── 不能解释 → 不允许提交
Step 4  执行验证 ─────────── 必须有可运行的验证 case
Step 5  提交 + 审计同步 ──── 变更记录到审计 md
```

### Bug 处理流程（6 步，目标：1h → 10min）

```
Step 1  定位范围 ── 哪个表 / 哪个模块 / 哪个 Pipeline Step
Step 2  Prompt 生成排查 SQL ── 按维度拆分
Step 3  对比数据 ── 当前 vs 预期
Step 4  修改代码
Step 5  验证结果 ── 跑通原始 case
Step 6  回归验证 ── 确认不影响其他 case
```

**强制要求**：不允许手工全量查，必须先用 SQL 拆维度定位。

# Phase 4 · 交付归档

## 4.1 迭代 PRD 模板

每个迭代周期输出一份 PRD，模板如下：

```markdown
# {产品名} · {迭代周期} 迭代 PRD

| 项目 | 说明 |
|------|------|
| 文档类型 | 功能迭代 PRD |
| 适用产品 | {产品名} |
| 版本分支 | `{分支名}` |
| 修订日期 | {日期} |

---

## {序号}. {功能名称}

### 背景
{一段话说明问题和动机}

### 方案
{方案描述 + 架构流程图（用 ASCII 即可）}

### 交互 / 前端
{交互表格：功能项 → 说明}

### 数据 / 后端
{数据源、接口变更、处理流程表格}

---

（重复以上结构，每个功能一节）

---

## 版本信息

| 项 | 值 |
|----|-----|
| 分支 | `{分支名}` |
| 基础分支 | `{基础分支}` |
| 提交 | `{commit hash}` |
| 远端 | `{remote 状态}` |
```

### 每个功能节的编写要点

| 板块 | 要写什么 | 不要写什么 |
|------|----------|------------|
| 背景 | 用户遇到什么问题、当前方案的缺陷 | 代码层面的技术细节 |
| 方案 | 整体流程、关键约束、数据流向 | 具体函数名、变量名 |
| 交互 | 用户视角的操作 → 系统反馈，用表格列举 | CSS 类名、DOM 结构 |
| 数据/后端 | 数据源、接口、处理步骤 | 代码实现、行号 |

## 4.2 审计文档

每次变更同步到对应审计文件：

| 类型 | 文件 | 记录内容 |
|------|------|----------|
| RAG / KAG 相关 | `事实rag变更审计.md` | 字段字典、检索层、路由规则、索引 |
| 工程 / 非 RAG | `NL2SQL工程变更审计.md` | Pipeline、SQL 生成器、Prompt、前端、维度映射 |

审计条目格式：

```markdown
## {日期} · {变更标题}

**触发场景**：{什么查询 / 什么操作触发了这个变更}

### 变更

| 文件 | 变更 | 说明 |
|------|------|------|
| ... | ... | ... |
```

## 4.3 Git 规范

| 规则 | 说明 |
|------|------|
| 分支命名 | `{月份}-week{N}-{起始日期}-{结束日期}`，如 `Apr-week0-3.30-4.3` |
| Commit 格式 | `feat/fix/chore(scope): 一句话描述` |
| 推送时机 | 迭代阶段性完成后推送，不做未验证的中间推送 |
| 不允许 | `push --force` 到 release / main，除非明确要求 |

# 附录 · 数据上下文清单

开发前必须能获取的结构化上下文（由数据产品维护）：

| 层级 | 内容 | 用途 |
|------|------|------|
| 表级 | 表名、中文描述、主键、分区键 | 选表 |
| 字段级 | 字段名、类型、中文描述、维度/指标 | 选字段 |
| 枚举级 | 字段名、合法取值列表、取值含义 | 防幻觉 |
| 指标路由 | 关键词 → 推荐表 + 口径 + 必需过滤 | 路由 |
| 维度映射 | 自然语言 → SQL 条件 | 过滤 |
| 埋点索引 | 功能描述 → entity 取值 + 截图 | 消歧 |

# 核心原则

```
1. 先想清楚，再动手       → 设计卡是入口
2. 人设计，AI 执行         → Cursor 是工具不是主人
3. 写的代码自己能解释       → 不能解释就不提交
4. 每个功能有验证闭环       → 没验证等于没做
5. 变更有记录可追溯         → PRD + 审计 + Git
```
